# Core frontend client

Owned files: `packages/core/` and this report. Python mesh/service logic and root tooling are owned by the parent.

## Implemented behavior

- `createMeshClient`, `useMesh`, `deriveTelemetry`, `deliveryLabel`, `roleNodes`, and all UI types are exported. Both phone views can share one client; its owner calls `dispose`.
- Default state is connected, explicitly replay mode, empty and ready for a user send. No message is sent automatically.
- Live transport uses the existing `/ws` state envelope and multipart `/send/text`, `/send/image`, `/send/voice`. HTTP, HTTPS, WS, WSS, and relative browser proxy endpoints are supported. Requests reject on unsuccessful HTTP responses, invalid response bodies, network failures, or a 15 second deadline. UI callers can retain their draft by clearing it only on success.
- A generation counter, socket identity checks, aborted HTTP requests, and cancelled timers isolate reset, endpoint/mode changes, and disposal. Reconnect uses exponential backoff bounded to five attempts after a connection loss. A live mode restart gives a new retry budget.
- Live snapshots replace aggregate message state, deduplicate undirected links, clamp received and acknowledged progress independently, and retain the last valid state on corrupt snapshots. Message IDs using reserved object keys are preserved in a record without a prototype.
- Legacy Python `delivered` means **ACK received**. Legacy live snapshots have no verified content, end-to-end integrity, terminal receipt, packet ledger, or trustworthy network metrics. Those remain unavailable. Backend preview text is never promoted into reconstructed recipient text.
- The actual `origin/packet-media-pipeline` implementation is supported at an isolated runtime boundary and now described by the published canonical OpenAPI 1.1 contract. Its `receiver_status=verified` establishes receiver integrity independently of sender receipt. Sender status must also be `delivered` before labeling **Delivered**. `awaiting_receipt` and `receipt_unconfirmed` remain explicit. Verified full text is fetched only from the exact expected same-backend `/messages/{id}/content` path, with a text/plain response; verified media receives a resolved URL to that same path. Text is retained across subsequent snapshots, and mode/session changes abort or ignore stale content fetches.
- Verified text content retries automatically, including when the final snapshot is the last update: maximum three attempts, 500/1000 ms backoff, and a 15 second deadline per attempt. Exhausted jobs stay cached so subsequent snapshots cannot cause infinite request churn. Final errors remain visible and explain that restarting live mode retries content; success clears the content error. Mode/endpoint changes, disposal, and backend restart generations cancel or invalidate pending retries.
- Packet branch events preserve real sequence and simulated channel-airtime timestamps. Rolling snapshots merge/deduplicate to a bounded 2000-event history. Sequence regression or simulation-clock regression clears history and content state for a same-endpoint backend restart. Per-hop receive/drop byte sizes are correlated only with one unambiguous prior transmit; otherwise the size stays null. No zero is invented for missing data. Partial/missing ring history makes cumulative receive totals unavailable. Observed loss uses published cumulative packet-attempt counters where available; earlier packet services need the trace completeness proof below. Message `radio_bytes`, `lost_packets`, and `retries` are authoritative measured totals even with a partial ledger. Simulation bitrate, nominal loss and configured `range_meters` are used when valid. Verified `receiver_verified_at` supplies time to receiver verification in simulation-scaled milliseconds; it includes queueing until reconstruction verifies, excludes the later sender receipt, and is not physical radio latency. Legacy services lacking these fields remain unavailable. `airtime_seconds` is retained as an airtime measurement and never renamed latency.
- Selected-message loss no longer depends on unrelated global event history: positive integer captured TX byte sizes must sum exactly to that message's cumulative backend `radio_bytes`. This proves its entire TX attempt count, allowing cumulative `lost_packets / captured TX count` even after joining an older session. Missing TX sizes, mismatched totals, or ring eviction leave loss unavailable. Receive byte totals retain their stricter history requirement; no latency/range metric is inferred from trace events.
- The backend team's canonical source originally landed at commit `3420fbb` and was refreshed verbatim from published packet/media commit `554957a` (OpenAPI 1.1): root `openapi.yaml` and generated `shared/typescript/api.ts`. `backend-types.ts` imports its `components`/`operations` type-only; UI media kind and base message statuses derive from those generated types, multipart requests and send response validations consume operation-derived types, and a test fixture uses `satisfies` on the generated MeshState. Optional canonical `created_at` becomes a null/unknown UI timestamp. The parent synchronized the backend-owned contract and generated files verbatim; core does not edit generated types. Published message status and media-kind runtime allowlists are checked against the generated unions, including cancelled/video/AI messages, while replay-only `reassembled` is explicit. Legacy minimal send responses validate operation-derived `Pick` fields so older services remain supported. Published `frames_sent` permits authoritative `lost_packets / frames_sent` independently of rolling event history.
- Replay traces are authored frontend fixtures, not a mesh simulator or evidence of radio performance. Six illustrative nodes include a Temple relay. Clear route: `node0 → node1 → node2 → node3 → node4`. Lossy route includes one dropped data transmission and one retransmission. Relay outage removes node2 and emits `route_changed` for connected alternative `node0 → node1 → node5 → node3 → node4`. Replies follow the reversed route.
- Text preserves user content and uses UTF-8 byte sizing without browser-only `TextEncoder`, including supplementary Unicode characters. Media actions produce clearly labeled sample voice/image metadata; no sample playback file or image reconstruction is supplied.
- Data, 12 byte chunk ACKs, and a 24 byte terminal receipt have explicit per-hop transmit/receive events. Packet byte metrics sum these actual fixture events, including retry transmissions. Receipt verification happens only after the authored receipt route completes. A single-byte, single-chunk clear fixture yields 148 transmitted and 148 received bytes across all links.
- Fixture config is explicitly illustrative: 5000 bps, 180 m range, and nominal loss 0 or 0.2 for the lossy preset. Trace-derived observed loss is separate from the nominal fixture setting. Timing is authored independently of that config. Single-chunk clean latency is 1680 ms; lossy adds 600 ms. Playback speed changes timer presentation, preserving authored timestamps and latency. A speed change applies to subsequent sends; already scheduled traces retain their starting speed.

## Backend telemetry handoff

The adapter consumes the backend-owned generated canonical wire contract. Runtime validation remains necessary for malformed JSON and mismatched servers. Packet/media fields are now published in canonical OpenAPI 1.1; missing legacy fields remain unavailable rather than inferred.

Future backend telemetry needs an explicit versioned event envelope, session identity, strictly increasing sequence, stable event and message IDs, actual packet ID, timestamp units, event kind, source/destination hop, and packet byte count. It must distinguish attempted transmission, actual receive, actual drop, retry, ACK, and terminal receipt. Route changes must report connected hop sequences or a truthful failure. Integrity verification and terminal receipt must come from the backend; aggregate ACK status cannot supply either. Media/text reconstruction needs a verified content reference with an integrity result before a live receiver can display it as reconstructed content.

Legacy live packet-event capability is false; the packet/media branch's real event array enables it. Additional ingestion requires schema ownership and test-first normalization, deduplication, reconnect/session isolation, sequence-gap handling, and proof that unknown or absent fields remain unavailable. Existing replay events are fixtures only and never fill live telemetry gaps.
